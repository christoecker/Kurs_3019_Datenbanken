    Prozeduren und Trigger (17.11.2026)

    Übung

    Worum geht es?

    Eben habt ihr den Zugriff auf die Daten geregelt: wer was lesen und ändern darf. Jetzt geht es um die Frage, wo Regeln und Abläufe leben, die mehr tun als Daten zu speichern. Zwei Mittel kennt eine Datenbank dafür: gespeicherte Prozeduren, die man ausdrücklich aufruft, und Trigger, die automatisch ausgelöst werden, wenn sich Daten ändern. Wir lesen, probieren und bewerten beides an BestTec. Am Ende steht die Frage, die in der Praxis wichtiger ist als die Syntax: Gehört eine Regel überhaupt in die Datenbank?

    Lernziele

    • Ihr könnt erklären, was eine gespeicherte Prozedur ist, und einen Aufruf mit Parametern lesen.
    • Ihr könnt vorhersagen, wann ein Trigger feuert und wie viele Zeilen er verarbeitet, und erklären, was inserted und deleted enthalten.
    • Ihr könnt begründen, ob eine Regel in eine Constraint, eine Prozedur, einen Trigger oder die Anwendung gehört.

    Ausgangslage: BestTec ca. 2 Min.

    Zwei neue Wünsche liegen vor. Der Prüfstand soll Testläufe nur noch über einen festen Weg melden, der vorher prüft, ob das Projekt existiert. Und die Personalabteilung möchte nachvollziehen können, wann welches Gehalt von welchem Wert auf welchen anderen geändert wurde. Dafür gibt es die neue Tabelle gehalt_log mit den Spalten lognr, manr, gehalt_alt, gehalt_neu, zeitpunkt und benutzer.

    Bleibt ihr direkt im Anschluss an die vorherige Einheit in derselben Datenbank, genügt Schritt 6. Sonst stellt ihr den Ausgangszustand mit diesen Skripten her, in dieser Reihenfolge:

    1. uebung-07-aufraeumen.sql
    2. uebung-05-besttec-datenbank.sql
    3. uebung-05-besttec-testdaten.sql
    4. uebung-07-besttec-testlauf.sql
    5. uebung-07-besttec-rechte-gesamt.sql
    6. uebung-08-besttec-gehaltlog.sql

    Eine gespeicherte Prozedur lesen und aufrufen ca. 8 Min.

    Eine gespeicherte Prozedur ist ein kleines Programm, das mit Namen in der Datenbank liegt. Man übergibt ihr Werte (Parameter), und sie führt mehrere Schritte aus: prüfen, rechnen, ändern. Sie läuft nur, wenn jemand sie ausdrücklich aufruft.

    Die Prozedur anlegen

    Der Prüfstand soll Testläufe über eine Prozedur melden. Welche Werte braucht sie als Eingabe? Was soll passieren, wenn es das gemeldete Projekt nicht gibt?

    Lösung 
    USE BestTec;
GO

-- Prozedur: einen Testlauf des Prüfstands melden
CREATE PROCEDURE p_testlauf_melden -- (1)!
    @prjnr    NUMERIC(3),
    @ergebnis VARCHAR(10)
AS
BEGIN
    SET NOCOUNT ON; -- (2)!

    -- Prüfung: Gibt es das Projekt überhaupt?
    IF NOT EXISTS (SELECT 1 FROM prj WHERE prjnr = @prjnr) -- (3)!
        THROW 50001, 'Unbekanntes Projekt.', 1; -- (4)!

    -- Nur wenn die Prüfung bestanden ist, wird der Testlauf eingetragen.
    INSERT INTO testlauf (prjnr, ergebnis) -- (5)!
    VALUES (@prjnr, @ergebnis);
END;
GO
    1. CREATE PROCEDURE legt die Prozedur an. Die Parameter beginnen in T-SQL mit @ und sind die Eingaben der Prozedur: das Projekt (@prjnr) und das Ergebnis (@ergebnis).
    2. SET NOCOUNT ON schaltet die Meldung „(n Zeilen betroffen)“ für die Anweisungen in der Prozedur ab. An den Daten ändert das nichts; aufrufende Programme (z. B. eine SPS) werden so nicht durch zusätzliche Meldungen gestört.
    3. EXISTS fragt nur, ob die Abfrage in den Klammern mindestens eine Zeile liefert. Welche Spalte sie auswählt, ist egal: SELECT 1 ist ein Platzhalter (SELECT * ginge genauso). Findet die Datenbank das Projekt, hört sie sofort auf zu suchen. NOT EXISTS dreht die Frage um: Die Bedingung ist wahr, wenn es das Projekt nicht gibt.
    4. THROW löst einen eigenen Fehler aus und beendet die Prozedur. Die drei Werte sind die Fehlernummer (ab 50000 für selbst definierte Fehler), der Fehlertext und der Status, eine frei wählbare Zahl von 0 bis 255, die die Stelle im Programm kennzeichnet (meist 1).
    5. testnr und zeitpunkt füllt die Datenbank selbst (IDENTITY bzw. DEFAULT), deshalb stehen sie nicht in der Spaltenliste.

    Die Prozedur trägt den Testlauf nur ein, wenn die Prüfung besteht.

    Die Prozedur aufrufen

    Mit EXEC ruft man eine Prozedur auf. Was erwartet ihr bei diesen drei Aufrufen?

    EXEC p_testlauf_melden @prjnr = 232, @ergebnis = 'bestanden';
EXEC p_testlauf_melden @prjnr = 999, @ergebnis = 'bestanden';
EXEC p_testlauf_melden @prjnr = 232, @ergebnis = 'unklar';
    Lösung 
    USE BestTec;
GO

-- 1. Gültiger Aufruf: Projekt 232 existiert, das Ergebnis ist erlaubt
EXEC p_testlauf_melden @prjnr = 232, @ergebnis = 'bestanden';
GO

-- 2. Unbekanntes Projekt: Fehler 50001 aus der Prozedur, es wird nichts eingetragen
EXEC p_testlauf_melden @prjnr = 999, @ergebnis = 'bestanden';
GO

-- 3. Unerlaubtes Ergebnis: Die Prozedur prüft das nicht selbst, aber der CHECK-Constraint
--    der Tabelle lehnt ab (Fehler 547)
EXEC p_testlauf_melden @prjnr = 232, @ergebnis = 'unklar';
GO

-- Kontrolle: Nur der erste Aufruf hat eine neue Zeile erzeugt
SELECT TOP 3 testnr, prjnr, zeitpunkt, ergebnis
FROM testlauf
ORDER BY testnr DESC;
GO

    Der erste Aufruf trägt den Testlauf ein. Der zweite scheitert mit Fehler 50001 aus der Prozedur: Das Projekt 999 gibt es nicht. Beim dritten Aufruf prüft die Prozedur nichts, aber die Tabelle wehrt sich: Der CHECK-Constraint erlaubt nur bestanden und fehlerhaft (Fehler 547). Regeln der Tabelle gelten also auch für Änderungen über eine Prozedur.

    Prozedur und Rechte ca. 5 Min.

    Der Prüfstand soll Testläufe künftig nur noch über die Prozedur melden. Was muss sich am Rechtekonzept aus der vorherigen Einheit ändern? Und wie prüft ihr, ob es wirkt?

    Lösung 
    USE BestTec;
GO

-- Der Prüfstand darf Testläufe nicht mehr direkt eintragen, sondern nur noch über die Prozedur.
REVOKE INSERT ON testlauf FROM r_pruefstand;
GRANT EXECUTE ON p_testlauf_melden TO r_pruefstand;
GO

EXECUTE AS USER = 'u_pruefstand';
GO
-- Direkter Zugriff auf die Tabelle: Fehler 229, INSERT-Recht fehlt
INSERT INTO testlauf (prjnr, ergebnis) VALUES (232, 'bestanden');
GO
-- Aufruf der Prozedur: funktioniert, obwohl der Prüfstand kein Recht auf testlauf hat
EXEC p_testlauf_melden @prjnr = 232, @ergebnis = 'bestanden';
GO
-- Auch die Prüfung in der Prozedur wirkt: unbekanntes Projekt wird abgelehnt (Fehler 50001)
EXEC p_testlauf_melden @prjnr = 999, @ergebnis = 'bestanden';
GO
-- Lesen darf der Prüfstand die Testläufe weiterhin nicht (Fehler 229)
SELECT * FROM testlauf;
GO
REVERT;
GO

    r_pruefstand verliert das INSERT-Recht auf testlauf und bekommt dafür EXECUTE auf die Prozedur. Ein direkter INSERT scheitert nun mit Fehler 229, der Aufruf der Prozedur funktioniert trotzdem: Prozedur und Tabelle gehören demselben Besitzer, deshalb prüft SQL Server nur das Recht auf die Prozedur — dasselbe Prinzip wie bei der Sicht in der vorherigen Einheit. Der Prüfstand kann jetzt nur noch tun, was die Prozedur zulässt, einschließlich ihrer Prüfung.

    Genau diese Konstruktion verwenden wir in Termin 7, wenn eine echte SPS Messdaten in die Datenbank schreibt: ein technischer Nutzer mit einer einzigen Berechtigung, nämlich EXECUTE auf eine Prozedur.

    Ein Trigger: Wann feuert er? ca. 10 Min.

    Die Prozedur schützt einen Weg in die Datenbank. Aber Gehälter lassen sich auch direkt mit einem UPDATE ändern, aus der Anwendung, aus SSMS oder aus einem Skript. Damit jede Änderung protokolliert wird, egal wie sie geschieht, braucht es etwas, das automatisch reagiert: einen Trigger.

    Den Trigger anlegen

    Wie beschreibt man, dass bei jedem UPDATE auf ma etwas passieren soll? Und woher weiß der Trigger, welche Zeilen sich geändert haben und wie ihre alten und neuen Werte lauten?

    Lösung 
    USE BestTec;
GO

-- Trigger: Jede Änderung des Gehalts in ma wird in gehalt_log protokolliert.
CREATE TRIGGER tr_ma_gehalt
ON ma
AFTER UPDATE -- (1)!
AS
BEGIN
    SET NOCOUNT ON; -- (2)!

    IF UPDATE(gehalt) -- (3)!
        INSERT INTO gehalt_log (manr, gehalt_alt, gehalt_neu)
        SELECT i.manr, d.gehalt, i.gehalt -- (4)!
        FROM inserted i, deleted d
        WHERE i.manr = d.manr -- (5)!
          AND i.gehalt <> d.gehalt; -- (6)!
END;
GO
    1. AFTER UPDATE legt fest, wann der Trigger läuft: nach jedem UPDATE auf ma, einmal pro Anweisung und nicht einmal pro Zeile. Direkt nach dem Anlegen ist er aktiv, ein extra Einschalten ist nicht nötig.
    2. SET NOCOUNT ON unterdrückt die Meldung „(n Zeilen betroffen)“ für die Anweisung im Trigger, damit sie nicht zusätzlich zur Meldung des auslösenden UPDATE erscheint.
    3. UPDATE(gehalt) ist wahr, wenn die Spalte gehalt in der SET-Klausel vorkommt, auch wenn ihr Wert gleich bleibt.
    4. inserted enthält die neuen Zustände, deleted die alten Zustände aller geänderten Zeilen. Beide Pseudotabellen gibt es nur innerhalb des Triggers.
    5. Die Verknüpfung über die Mitarbeiternummer führt alten und neuen Zustand derselben Zeile zusammen. Ohne sie entstünde das Kreuzprodukt (Fehlerbild F1).
    6. Der Vergleich behält nur Zeilen, deren Gehalt sich wirklich geändert hat.

    Weil der Trigger einmal pro Anweisung läuft, verarbeitet er bei einem UPDATE auf viele Zeilen alle auf einmal.

    Die Wirkung vorhersagen

    Wie viele Zeilen stehen nach jeder dieser Anweisungen in gehalt_log? Leert vor jeder Anweisung das Protokoll mit TRUNCATE TABLE gehalt_log;.

    • (a) UPDATE ma SET gehalt = 3000 WHERE manr = 7329; (Frohn verdient bisher 2900)
    • (b) UPDATE ma SET gehalt = gehalt * 1.05 WHERE abtnr = 20;
    • (c) UPDATE ma SET job = 'Entwickler' WHERE manr = 7329;
    • (d) UPDATE ma SET gehalt = gehalt WHERE abtnr = 20;
    • (e) UPDATE ma SET gehalt = 0 WHERE abtnr = 99; (diese Abteilung gibt es nicht)
    Lösung 
    USE BestTec;
GO

-- 1. Gehalt eines einzelnen Mitarbeiters ändern (Frohn: 2900 -> 3000)
TRUNCATE TABLE gehalt_log;
UPDATE ma SET gehalt = 3000 WHERE manr = 7329;
SELECT manr, gehalt_alt, gehalt_neu FROM gehalt_log;        -- 1 Zeile
GO

-- 2. Gehälter der Abteilung 20 um 5 % erhöhen: ein UPDATE, sechs betroffene Zeilen
TRUNCATE TABLE gehalt_log;
UPDATE ma SET gehalt = gehalt * 1.05 WHERE abtnr = 20;
SELECT manr, gehalt_alt, gehalt_neu FROM gehalt_log;        -- 6 Zeilen: der Trigger lief einmal, aber für alle sechs
GO

-- 3. Nur die Tätigkeit ändern: Die Spalte gehalt kommt in SET nicht vor
TRUNCATE TABLE gehalt_log;
UPDATE ma SET job = 'Entwickler' WHERE manr = 7329;
SELECT manr, gehalt_alt, gehalt_neu FROM gehalt_log;        -- 0 Zeilen
GO

-- 4. Gehalt wird "geändert", behält aber seinen Wert
TRUNCATE TABLE gehalt_log;
UPDATE ma SET gehalt = gehalt WHERE abtnr = 20;
SELECT manr, gehalt_alt, gehalt_neu FROM gehalt_log;        -- 0 Zeilen: UPDATE(gehalt) ist wahr, aber gehalt_alt = gehalt_neu
GO

-- 5. UPDATE ohne passende Zeile: Es gibt keine Abteilung 99
TRUNCATE TABLE gehalt_log;
UPDATE ma SET gehalt = 0 WHERE abtnr = 99;                  -- 0 Zeilen betroffen
SELECT manr, gehalt_alt, gehalt_neu FROM gehalt_log;        -- 0 Zeilen: Der Trigger lief, aber inserted war leer
GO
    Anweisung Logzeilen Begründung
    (a) 1 Eine Zeile geändert, das Gehalt ist anders.
    (b) 6 Ein Trigger-Lauf für sechs Zeilen: inserted und deleted enthalten alle Mitarbeiter der Abteilung 20.
    (c) 0 gehalt kommt in SET nicht vor, UPDATE(gehalt) ist falsch.
    (d) 0 UPDATE(gehalt) ist wahr, aber alter und neuer Wert sind gleich; der Vergleich filtert alle Zeilen heraus.
    (e) 0 Der Trigger läuft trotzdem (AFTER UPDATE), aber inserted ist leer.

    Ein DELETE oder INSERT auf ma löst diesen Trigger nicht aus, denn er ist nur für UPDATE angelegt. Genau darüber stolpern Trigger, die von KI erzeugt wurden: Sie feuern zu oft, zu selten oder verarbeiten nur eine Zeile (Fehlerbild F16 und F18).

    Trigger verwalten und Nebenwirkungen ca. 6 Min.

    Ein zweiter Trigger soll Gehaltssenkungen verbieten. Was passiert, wenn ein UPDATE sechs Gehälter senkt und der Trigger eingreift? Was geschieht mit dem Protokoll des ersten Triggers? Und wie schaltet man einen Trigger ab und wieder an?

    Lösung 
    USE BestTec;
GO

-- Zweiter Trigger: Gehaltssenkungen sind nicht erlaubt.
CREATE TRIGGER tr_ma_gehalt_senkung
ON ma
AFTER UPDATE
AS
BEGIN
    IF EXISTS (SELECT 1 -- (1)!
               FROM inserted i, deleted d
               WHERE i.manr = d.manr
                 AND i.gehalt < d.gehalt)
        THROW 50002, 'Gehaltssenkungen sind nicht erlaubt.', 1; -- (2)!
END;
GO

-- Test: Alle sechs Gehälter der Abteilung 20 sollen um 100 sinken
TRUNCATE TABLE gehalt_log;
UPDATE ma SET gehalt = gehalt - 100 WHERE abtnr = 20;       -- Fehler 50002
GO
SELECT name, gehalt FROM ma WHERE abtnr = 20;               -- unverändert: auch nicht die Zeilen, die "gepasst" hätten
SELECT COUNT(*) AS logzeilen FROM gehalt_log;               -- 0: auch das Protokoll von tr_ma_gehalt wurde zurückgenommen
GO

-- Trigger verwalten: Status ansehen, abschalten, wieder einschalten, löschen
SELECT name, is_disabled FROM sys.triggers WHERE parent_id = OBJECT_ID('ma');
GO

DISABLE TRIGGER tr_ma_gehalt_senkung ON ma;                 -- ausschalten
GO
UPDATE ma SET gehalt = gehalt - 100 WHERE abtnr = 20;       -- funktioniert jetzt (und wird protokolliert)
GO
SELECT COUNT(*) AS logzeilen FROM gehalt_log;               -- 6
GO

ENABLE TRIGGER tr_ma_gehalt_senkung ON ma;                  -- wieder einschalten
GO

DROP TRIGGER tr_ma_gehalt_senkung;                          -- entfernen
GO
    1. EXISTS fragt, ob es mindestens eine Zeile gibt, deren neues Gehalt kleiner ist als das alte. Das SELECT 1 ist nur ein Platzhalter (siehe Prozedur oben).
    2. THROW im Trigger bricht die ganze UPDATE-Anweisung ab, und alle Änderungen werden zurückgenommen.

    Kein Gehalt ändert sich, und im Protokoll bleibt nichts zurück. Der Grund: Das UPDATE und alle Trigger, die es auslöst, laufen in einer Transaktion. Bricht ein Trigger mit einem Fehler ab, wird alles zurückgenommen, auch das, was ein anderer Trigger schon geschrieben hat. Nur wenn alle Trigger durchlaufen, bleiben die Änderungen bestehen. Steht das UPDATE selbst in einer BEGIN TRANSACTION-Klammer, wird sogar diese ganze Transaktion zurückgenommen. Das ist eine wichtige Nebenwirkung: Ein Fehler im Trigger lässt den Datenzugriff scheitern, der ihn ausgelöst hat.

    Verwalten:

    • DISABLE TRIGGER … ON … schaltet einen Trigger ab, er bleibt aber bestehen.
    • ENABLE TRIGGER … ON … schaltet ihn wieder ein.
    • DROP TRIGGER … entfernt ihn ganz.
    • sys.triggers zeigt alle Trigger und ihren Zustand (is_disabled).

    Weitere Nebenwirkungen: Ein Trigger läuft unsichtbar mit. Wer nur den UPDATE sieht, ahnt nicht, dass ein zweiter Schreibvorgang stattfindet. Bei großen Änderungen kostet er Zeit. Er darf in Tabellen schreiben, auf die der auslösende Benutzer kein Recht hat. Und hängen mehrere Trigger an derselben Tabelle, ist ihre Reihenfolge nicht festgelegt; sie sollten deshalb nicht voneinander abhängen.

    Wohin mit der Logik? ca. 7 Min.

    Prüfregeln, Abläufe und Protokolle können an vier Orten leben. Jeder passt zu einer anderen Art von Anforderung:

    • Constraint — wenn die Regel nur Werte betrifft: ein erlaubter Wertebereich, eine Liste erlaubter Werte, Eindeutigkeit, ein Fremdschlüssel. Das ist die erste Wahl, denn eine Constraint ist einfach, schnell und gilt automatisch für jeden Zugriffsweg, ganz ohne Programmcode.
    • Prozedur — wenn es einen festen Weg geben soll, der mehrere Schritte zusammenfasst (erst prüfen, dann eintragen) und den man gezielt freigeben möchte, z. B. für ein Gerät, das nicht direkt auf die Tabellen zugreifen soll. Eine Prozedur wirkt aber nur, wenn sie aufgerufen wird; wer Tabellenrechte hat, kann sie umgehen.
    • Trigger — wenn bei jeder Änderung automatisch etwas geschehen muss, egal wer sie wie ausführt, und eine Constraint dafür nicht reicht: typisch sind Protokollieren und Archivieren. Der Preis: Ein Trigger läuft unsichtbar mit, hat Nebenwirkungen und ist schwerer zu testen. Man setzt ihn deshalb nur ein, wenn nichts Einfacheres genügt.
    • Anwendung — wenn die Aufgabe nicht zur Datenhaltung gehört: Darstellung, Berechnungen für eine Oberfläche, Aktionen außerhalb der Datenbank wie E-Mails oder andere Systeme. Gilt die Regel nur für diese eine Anwendung, kann sie auch dort leben.

    Ordnet diese Anforderungen zu und begründet die Wahl. Denkt an Konsistenz (gilt die Regel für jeden Zugriffsweg?), Wartbarkeit und Testbarkeit.

    Anforderung Wohin?
    1. Ein Gehalt darf nie negativ sein.
    2. Jede Änderung eines Gehalts soll nachvollziehbar sein, egal wer sie wie ausführt.
    3. Der Prüfstand soll Testläufe nur über einen festen Weg melden, der das Projekt prüft.
    4. Gehälter sollen in der Oberfläche als „4.800,00 €“ angezeigt werden.
    5. Bei einem fehlerhaften Testlauf soll der Projektleiter eine E-Mail bekommen.
    Lösung
    Anforderung Wohin? Begründung
    1. Gehalt nie negativ Constraint (CHECK (gehalt > 0)) Einfache Wertregel, gilt für jeden Zugriffsweg, deklarativ und schnell.
    2. Gehaltsänderungen nachvollziehbar Trigger Muss für jeden Zugriffsweg gelten (Anwendung, SSMS, Skript) und darf nicht von einer Anwendung vergessen werden.
    3. Fester Weg für Testläufe Prozedur mit EXECUTE-Recht Ein definierter Einstieg mit zentraler Prüfung; der Prüfstand braucht kein Tabellenrecht.
    4. Anzeige als „4.800,00 €“ Anwendung Reine Darstellung, gehört nicht in die Datenbank.
    5. E-Mail bei fehlerhaftem Testlauf Anwendung (oder ein Dienst) Eine Aktion außerhalb der Datenbank. Im Trigger würde sie jede Meldung verlangsamen, und ein Mailfehler ließe die Meldung scheitern.

    Gesamtergebnis ca. 2 Min.

    Lösung
    Mittel Wann es greift Gut für Worauf achten
    Constraint bei jeder Änderung, automatisch einfache Wertregeln (CHECK, UNIQUE, Fremdschlüssel) kann nichts protokollieren oder berechnen
    Prozedur nur wenn sie aufgerufen wird ein fester Weg mit Prüfung, Rechte über EXECUTE wird umgangen, wenn Tabellenrechte offen sind
    Trigger automatisch bei INSERT, UPDATE oder DELETE Regeln und Protokolle für jeden Zugriffsweg unsichtbar; läuft einmal pro Anweisung für alle Zeilen; ein Fehler macht die Änderung rückgängig
    Anwendung im Programm Darstellung, Berechnung, externe Aktionen Regeln gelten nicht für andere Zugriffswege

    Als Faustregel gilt: Was für jeden Zugriffsweg gelten muss, gehört in die Datenbank, und zwar so einfach wie möglich (erst Constraint, dann Trigger oder Prozedur). Alles andere gehört in die Anwendung.

    In SQL Server feuern Trigger einmal pro Anweisung und nicht pro Zeile; alte und neue Werte stehen in deleted und inserted. Andere Datenbanksysteme arbeiten zeilenweise mit BEFORE, OLD und NEW (siehe SQL Server und Lehrbuch/Lehrbrief: Abweichungen). Neben AFTER kennt SQL Server auch INSTEAD OF, ein Trigger, der die auslösende Anweisung ersetzt; den brauchen wir hier nicht.

    Betreutes Selbststudium

    Worum geht es?

    Trigger sind mächtig und gefährlich zugleich: Sie laufen unsichtbar mit, und kleine Fehler fallen oft erst bei Massenänderungen auf. Ihr müsst keinen Trigger selbst von Grund auf schreiben. Wichtiger ist, dass ihr einen Trigger lesen, seine Wirkung vorhersagen und einen Vorschlag der KI beurteilen könnt: Feuert er zur richtigen Zeit? Verarbeitet er alle betroffenen Zeilen? Passt die Syntax zu SQL Server? Dazu kommt die Entscheidung, ob eine Regel überhaupt in die Datenbank gehört.

    Lernziele

    • Ihr könnt die Wirkung eines Triggers auf verschiedene Anweisungen vorhersagen.
    • Ihr könnt einen Trigger mit KI-Unterstützung erzeugen, ihn erklären, aktivieren und deaktivieren.
    • Ihr könnt fehlerhafte Trigger an typischen Merkmalen erkennen.
    • Ihr könnt begründen, ob eine Anforderung in die Datenbank oder in die Anwendung gehört.

    Teil A — Die Wirkung eines Triggers vorhersagen ca. 8 Min.

    Ein Kollege hat diesen Trigger geschrieben, um alle Gehaltsänderungen zu protokollieren. Legt ihn an (den Trigger aus der Übung entfernt ihr vorher mit DROP TRIGGER IF EXISTS tr_ma_gehalt;):

    CREATE TRIGGER tr_ma_gehalt_v2
ON ma
AFTER UPDATE
AS
BEGIN
    INSERT INTO gehalt_log (manr, gehalt_alt, gehalt_neu)
    SELECT i.manr, d.gehalt, i.gehalt
    FROM inserted i, deleted d
    WHERE i.manr = d.manr;
END;

    Teil C — Fehlerhafte Trigger erkennen ca. 11 Min.

    Vier Trigger sollen „jede Gehaltsänderung protokollieren“. Drei davon enthalten typische Fehler, einer ist korrekt. Entfernt vorher alle früheren Trigger auf ma:

    DROP TRIGGER IF EXISTS tr_ma_gehalt;
DROP TRIGGER IF EXISTS tr_ma_gehalt_v2;
DROP TRIGGER IF EXISTS tr_ma_gehalt_v3;

    Prüft jeden Trigger mit diesem Test (6 Mitarbeiter der Abteilung 20, also 6 Logzeilen erwartet) und löscht ihn danach wieder:

    TRUNCATE TABLE gehalt_log;
UPDATE ma SET gehalt = gehalt * 1.05 WHERE abtnr = 20;
SELECT manr, gehalt_alt, gehalt_neu FROM gehalt_log;

    Sagt vorher, was jeder Trigger liefert, was falsch ist und welches Fehlerbild vorliegt (Fehlerbildkatalog).

    1. Trigger C.1

    CREATE TRIGGER tr_ma_gehalt_c1
ON ma
AFTER UPDATE
AS
BEGIN
    DECLARE @manr NUMERIC(4), @alt NUMERIC(9,2), @neu NUMERIC(9,2);
    SELECT @manr = manr, @neu = gehalt FROM inserted;
    SELECT @alt = gehalt FROM deleted;
    INSERT INTO gehalt_log (manr, gehalt_alt, gehalt_neu)
    VALUES (@manr, @alt, @neu);
END;

    2. Trigger C.2

    CREATE TRIGGER tr_ma_gehalt_c2
BEFORE UPDATE ON ma
FOR EACH ROW
BEGIN
    INSERT INTO gehalt_log (manr, gehalt_alt, gehalt_neu)
    VALUES (OLD.manr, OLD.gehalt, NEW.gehalt);
END;

    3. Trigger C.3

    CREATE TRIGGER tr_ma_gehalt_c3
ON ma
AFTER UPDATE
AS
BEGIN
    INSERT INTO gehalt_log (manr, gehalt_alt, gehalt_neu)
    SELECT i.manr, d.gehalt, i.gehalt
    FROM inserted i, deleted d;
END;

    4. Trigger C.4

    CREATE TRIGGER tr_ma_gehalt_c4
ON ma
AFTER UPDATE
AS
BEGIN
    SET NOCOUNT ON;
    IF UPDATE(gehalt)
        INSERT INTO gehalt_log (manr, gehalt_alt, gehalt_neu)
        SELECT i.manr, d.gehalt, i.gehalt
        FROM inserted i, deleted d
        WHERE i.manr = d.manr
          AND i.gehalt <> d.gehalt;
END;
