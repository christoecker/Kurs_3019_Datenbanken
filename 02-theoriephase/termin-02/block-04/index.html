    Relationenschema in SQL Server anlegen (27.10.2026)

    Übung

    Worum geht es?

    Bisher habt ihr Datenbanken entworfen: erst als ER-Modell, dann als Relationenschema, zuletzt normalisiert. Jetzt macht ihr den nächsten Schritt und bringt ein Schema in eine echte Datenbank: Ihr legt Datenbank und Tabellen in SQL Server an. In Woche 11 der Praxisphase habt ihr solche Skripte schon ausgeführt — heute schreibt ihr sie selbst, und ihr lernt, wie ihr der Datenbank mit sogenannten Constraints die Regeln eurer Anwendungswelt beibringt, damit sie fehlerhafte Daten selbstständig ablehnt.

    Lernziele

    • Ihr könnt ein Relationenschema Schritt für Schritt in T-SQL umsetzen: Wertebereiche werden zu Datentypen, Schlüssel zu PRIMARY KEY und FOREIGN KEY.
    • Ihr könnt erklären, welche Regel ein Constraint (UNIQUE, CHECK, DEFAULT) absichert, und vorhersagen, welche Datenänderung die Datenbank daraufhin ablehnt.
    • Ihr könnt begründen, warum Tabellen in einer bestimmten Reihenfolge angelegt werden müssen.

    Kurzer Rückblick ca. 4 Min.

    1. Was passiert in der letzten Phase des Datenbankentwurfs, der Datendefinition?

      Musterlösung anzeigen

      Das logische Schema (hier: das Relationenschema) wird in die Datenstrukturen einer Datenbanksprache umgesetzt — bei uns also in SQL-Anweisungen, die die Tabellen im Datenbanksystem anlegen.

    2. Wie erkennt man im Relationenschema einen Primärschlüssel und einen Fremdschlüssel, und wofür sind sie da?

      Musterlösung anzeigen

      Der Primärschlüssel (PK) ist das Attribut bzw. die Attributkombination, die jeden Datensatz einer Relation eindeutig identifiziert. Ein Fremdschlüssel (FK) verweist auf den Schlüssel einer anderen Relation und bildet so die Beziehung zwischen den Datensätzen ab.

    3. Eine Tabelle AUFTRAG hat einen Fremdschlüssel auf die Tabelle KUNDE. Was muss gelten, damit ein neuer Datensatz in AUFTRAG überhaupt eingetragen werden kann — und was bedeutet das für die Reihenfolge, in der man Daten einträgt?

      Musterlösung anzeigen

      Wegen der Fremdschlüsselintegrität muss der Kunde, auf den der Auftrag verweist, bereits in KUNDE existieren. Ein Auftrag kann also erst eingetragen werden, wenn die Beziehung zu einem vorhandenen Datensatz der anderen Tabelle hergestellt werden kann. Daten müssen deshalb zuerst in die Tabelle, auf die verwiesen wird (KUNDE), und erst danach in die verweisende Tabelle (AUFTRAG).

    Das Szenario: Kompressor-Datenbank wird real ca. 2 Min.

    Das Datenmodell der Kompressor-Zustandsüberwachung von Pustefix & Co. kennt ihr aus der Normalisierungs-Übung: Am Kompressor werden minütlich Messwerte gespeichert, einmal täglich läuft ein Analyse-Lauf, der mit mehreren Auswertealgorithmen Schädigungswerte berechnet und lokale Extremwerte der Druckdifferenz verarbeitet. Dieses Modell besteht aus sechs Relationen: MESSUNG, VERFAHREN, ALGORITHMUS, ANALYSE_LAUF, SCHAEDIGUNG und EXTREMWERT. Heute legt ihr diese sechs Tabellen auf eurem eigenen Rechner an — in SQL Server.

    Datenbank und Tabellen anlegen ca. 19 Min.

    Die Datenbank

    Zuerst braucht ihr eine leere Datenbank, in der die Tabellen entstehen sollen. Welche Anweisung legt eine neue Datenbank an, und wie sagt ihr SQL Server anschließend, dass die folgenden Anweisungen in dieser Datenbank ausgeführt werden sollen?

    Lösung 
    CREATE DATABASE Kompressor; -- (1)!
GO -- (2)!
USE Kompressor; -- (3)!
GO
    1. CREATE DATABASE legt die Datenbank an.
    2. GO ist, wie in Woche 11, kein SQL-Befehl, sondern ein SSMS-Kommando: Es trennt das Skript in einzelne Ausführungsblöcke (sogenannte Batches). Ohne GO hinter CREATE DATABASE würde USE versuchen, in eine Datenbank zu wechseln, die zu diesem Zeitpunkt noch nicht existiert.
    3. USE wechselt in die Datenbank; alle folgenden Anweisungen gelten dort.

    Erste Tabelle: MESSUNG

    Beginnen wir mit der Relation, die keine Verbindung zu den anderen hat:

    Relation MESSUNG

    Schlüssel Attribut Wertebereich optional?
    PK zeitstempel datetime nein
    – druck_eingang decimal nein
    – druck_ausgang decimal nein
    – volumenstrom decimal nein
    – temperatur decimal nein
    – luftfeuchtigkeit decimal nein

    Das Relationenschema nennt nur "decimal" und "datetime" — SQL Server will es genauer wissen. Überlegt: Wie viele Stellen braucht ein Druckwert in bar, wie viele Nachkommastellen sind bei einer minütlichen Messung sinnvoll? Wie genau muss der Zeitstempel sein?

    Lösung 
    CREATE TABLE MESSUNG (
    zeitstempel       DATETIME2(0)  NOT NULL PRIMARY KEY, -- (1)!
    druck_eingang     DECIMAL(6,2)  NOT NULL, -- (2)!
    druck_ausgang     DECIMAL(6,2)  NOT NULL,
    volumenstrom      DECIMAL(8,2)  NOT NULL,
    temperatur        DECIMAL(5,2)  NOT NULL,
    luftfeuchtigkeit  DECIMAL(5,2)  NOT NULL
);
    1. DATETIME2(0) speichert den Zeitstempel sekundengenau, bei einer minütlichen Messung genügt das. PRIMARY KEY direkt hinter dem Attribut ist die übliche Kurzschreibweise; der Primärschlüssel ist ohnehin nie leer. Sie hat einen kleinen Nachteil: SQL Server vergibt den Namen des Schlüssels dabei selbst (im Object Explorer unter der Tabelle bei Keys einsehbar). Wie ihr Schlüsseln einen eigenen Namen gebt, schauen wir uns im Abschnitt zu den Constraints an.
    2. DECIMAL(6,2) erlaubt z. B. Werte bis 9999,99 mit zwei Nachkommastellen — für Druck in bar und andere Prozessgrößen reichlich. NOT NULL steht bei jedem Attribut, das im Schema "nicht optional" war.

    Aus dem Wertebereich wird ein konkreter Datentyp:

    Wertebereich im Relationenschema Datentyp in SQL Server
    int INT
    decimal DECIMAL(p,s) — p Stellen insgesamt, davon s nach dem Komma
    string VARCHAR(n) — höchstens n Zeichen
    date DATE
    datetime DATETIME2(n) — n Nachkommastellen bei den Sekunden

    VERFAHREN und ALGORITHMUS

    Jetzt kommen zwei Relationen mit einer Fremdschlüsselbeziehung:

    Relation VERFAHREN

    Schlüssel Attribut Wertebereich optional?
    PK verfahren string nein
    – grenzwert_meldung int nein
    – grenzwert_alarm int nein

    Relation ALGORITHMUS

    Schlüssel Attribut Wertebereich optional?
    PK algorithmus_id int nein
    FK verfahren string nein
    – version string nein
    – release_datum date nein
    – status string nein

    Zwei Fragen dazu: In welcher Reihenfolge müssen die beiden Tabellen angelegt werden? Und algorithmus_id ist ein künstlicher Schlüssel (ein Surrogatschlüssel) — muss man die Nummern wirklich bei jedem neuen Algorithmus selbst vergeben?

    Lösung 
    CREATE TABLE VERFAHREN (
    verfahren          VARCHAR(20)  NOT NULL PRIMARY KEY,
    grenzwert_meldung  INT          NOT NULL,
    grenzwert_alarm    INT          NOT NULL
);

CREATE TABLE ALGORITHMUS (
    algorithmus_id  INT IDENTITY(1,1)  NOT NULL PRIMARY KEY, -- (1)!
    verfahren       VARCHAR(20)        NOT NULL,
    ver             VARCHAR(10)        NOT NULL,
    release_datum   DATE               NOT NULL,
    release_status  VARCHAR(10)        NOT NULL,
    FOREIGN KEY (verfahren) REFERENCES VERFAHREN(verfahren) -- (2)!
);
    1. IDENTITY(1,1) lässt SQL Server die Nummern selbst vergeben (Startwert 1, Schrittweite 1). Beim INSERT lässt man die Spalte einfach weg. Das ist die übliche Umsetzung eines Surrogatschlüssels; Lücken in der Nummernfolge sind dabei normal (z. B. wenn ein INSERT scheitert).
    2. Der Fremdschlüssel verweist auf VERFAHREN(verfahren), und SQL Server prüft schon beim Anlegen, ob das Ziel existiert. Deshalb muss VERFAHREN zuerst angelegt werden. Auch die FOREIGN KEY-Zeile ist eine Kurzschreibweise, bei der SQL Server den Namen vergibt.

    Abweichung vom Relationenschema: In ALGORITHMUS heißen zwei Spalten anders als in der Tabelle oben — version wurde zu ver und status zu release_status. Beide Wörter haben in T-SQL eine besondere Bedeutung bzw. sind als Schlüsselwörter belegt. Als Spaltennamen führen solche Wörter schnell zu Verwechslungen und zu Fehlern, die man erst suchen muss (je nach Fall müsste man sie in eckige Klammern setzen). Im Relationenschema stören sie nicht, es ist ja noch kein SQL; beim Umsetzen weicht man deshalb auf einen unkritischen Namen aus. Das ist ein typischer Fall, in dem sich die Implementierung bewusst vom Entwurf unterscheidet — die Abweichung gehört dokumentiert. Auch im weiteren Verlauf der Übung heißen die Spalten ver und release_status.

    ANALYSE_LAUF, SCHAEDIGUNG und EXTREMWERT

    Die drei restlichen Relationen:

    Relation ANALYSE_LAUF

    Schlüssel Attribut Wertebereich optional?
    PK analyse_lauf_id int nein
    – zeitstempel datetime nein

    Relation SCHAEDIGUNG

    Schlüssel Attribut Wertebereich optional?
    PK, FK analyse_lauf_id int nein
    PK, FK algorithmus_id int nein
    – schaedigungswert int (0–100) nein

    Relation EXTREMWERT

    Schlüssel Attribut Wertebereich optional?
    PK zeitstempel datetime nein
    – typ string (Maximum/Minimum) nein
    – wert decimal nein
    – verarbeitet boolean nein

    SCHAEDIGUNG hat einen Primärschlüssel aus zwei Attributen, die beide gleichzeitig Fremdschlüssel sind. Wie schreibt man das auf? Und welchen Datentyp hat ein "boolean" in SQL Server?

    Lösung 
    CREATE TABLE ANALYSE_LAUF (
    analyse_lauf_id  INT IDENTITY(1,1)  NOT NULL PRIMARY KEY,
    zeitstempel      DATETIME2(0)       NOT NULL
);

CREATE TABLE SCHAEDIGUNG (
    analyse_lauf_id   INT  NOT NULL,
    algorithmus_id    INT  NOT NULL,
    schaedigungswert  INT  NOT NULL,
    PRIMARY KEY (analyse_lauf_id, algorithmus_id), -- (1)!
    FOREIGN KEY (analyse_lauf_id) REFERENCES ANALYSE_LAUF(analyse_lauf_id), -- (2)!
    FOREIGN KEY (algorithmus_id)  REFERENCES ALGORITHMUS(algorithmus_id)
);

CREATE TABLE EXTREMWERT (
    zeitstempel  DATETIME2(0)  NOT NULL PRIMARY KEY,
    typ          VARCHAR(7)    NOT NULL,
    wert         DECIMAL(6,2)  NOT NULL,
    verarbeitet  BIT           NOT NULL -- (3)!
);
    1. Ein zusammengesetzter Primärschlüssel wird nicht mehr direkt hinter das Attribut geschrieben, sondern als eigene Zeile PRIMARY KEY (a, b) unter die Attribute.
    2. Genauso stehen die beiden Fremdschlüssel jeweils als eigene Zeile FOREIGN KEY (...) REFERENCES ....
    3. Für den Wahrheitswert gibt es in SQL Server keinen Typ BOOLEAN, stattdessen BIT (0 oder 1).

    Die Tabellen sind damit angelegt, aber noch nicht abgesichert: Nichts verhindert bisher, dass jemand einen Schädigungswert von 250 % einträgt oder den Freigabestatus eines Algorithmus mit "fertig" angibt.

    Constraints: die Regeln der Datenbank ca. 16 Min.

    Was Constraints leisten

    Eine Datenbank soll nicht jeden Wert annehmen, der ihr angeboten wird. Mit Constraints (Einschränkungen) legt ihr fest, welche Regeln der Anwendungswelt das Datenbanksystem selbst durchsetzt — unabhängig davon, welches Programm oder welche Person Daten einträgt. Ein paar davon kennt ihr schon, ohne sie so genannt zu haben:

    Constraint Frage, die er beantwortet Beispiel im Kompressor-Modell
    NOT NULL Muss ein Wert vorhanden sein? alle Messwerte
    PRIMARY KEY Wie wird ein Datensatz eindeutig identifiziert? zeitstempel in MESSUNG
    FOREIGN KEY Muss der Verweis auf einen vorhandenen Datensatz zeigen? ALGORITHMUS.verfahren
    UNIQUE Darf ein Wert (oder eine Kombination) nur einmal vorkommen, obwohl er nicht Primärschlüssel ist? siehe unten
    CHECK Liegt der Wert in einem zulässigen Bereich oder einer Liste? siehe unten
    DEFAULT Welcher Wert gilt, wenn keiner angegeben wird? siehe unten

    Regeln aus dem Szenario ableiten und nachrüsten

    Aus dem Szenario ergeben sich noch ein paar Regeln, die die Tabellen bisher nicht durchsetzen:

    1. Verfahren und Version (ver) zusammen legen einen Algorithmus eindeutig fest.
    2. Zu jedem Zeitpunkt gibt es höchstens einen Analyse-Lauf.
    3. Schädigungswerte sind Prozentangaben zwischen 0 und 100.
    4. Die Melde- und Alarm-Grenzwerte eines Verfahrens sind ebenfalls Prozentangaben zwischen 0 und 100.
    5. Der Freigabestatus (release_status) eines Algorithmus ist alpha, beta oder stable.
    6. Ein Extremwert ist entweder ein Maximum oder ein Minimum.
    7. Ein neu erfasster Extremwert gilt zunächst als unverarbeitet.

    Ordnet jeder Regel den passenden Constraint zu und rüstet sie mit ALTER TABLE nachträglich an den bestehenden Tabellen nach. Die Grundform lautet:

    ALTER TABLE <Tabelle>
    ADD CONSTRAINT <Name> <Definition>;

    Für <Definition> kommen die Constraint-Arten aus der Tabelle oben in Frage:

    Constraint <Definition>
    PRIMARY KEY PRIMARY KEY (spalte [, spalte ...])
    FOREIGN KEY FOREIGN KEY (spalte) REFERENCES zieltabelle(zielspalte)
    UNIQUE UNIQUE (spalte [, spalte ...])
    CHECK CHECK (bedingung)
    DEFAULT DEFAULT wert FOR spalte

    (Primär- und Fremdschlüssel gibt es in unseren Tabellen schon; für die sieben Regeln unten braucht ihr nur UNIQUE, CHECK und DEFAULT.)

    Gebt jedem Constraint einen sprechenden Namen nach dem Schema PK_ / FK_ / UQ_ / CK_ / DF_ + Tabelle + Gegenstand, z. B. UQ_ANALYSE_LAUF_ZEITSTEMPEL.

    Lösung 
    -- UNIQUE: Verfahren + Version legen einen Algorithmus eindeutig fest
ALTER TABLE ALGORITHMUS
    ADD CONSTRAINT UQ_ALGORITHMUS_VERFAHREN_VER UNIQUE (verfahren, ver); -- (1)!

-- UNIQUE: pro Zeitpunkt gibt es genau einen Analyse-Lauf
ALTER TABLE ANALYSE_LAUF
    ADD CONSTRAINT UQ_ANALYSE_LAUF_ZEITSTEMPEL UNIQUE (zeitstempel);

-- CHECK: Schädigungswerte und Grenzwerte sind Prozentangaben
ALTER TABLE SCHAEDIGUNG
    ADD CONSTRAINT CK_SCHAEDIGUNG_WERT
    CHECK (schaedigungswert BETWEEN 0 AND 100); -- (2)!

ALTER TABLE VERFAHREN
    ADD CONSTRAINT CK_VERFAHREN_GRENZWERTE
    CHECK (grenzwert_meldung BETWEEN 0 AND 100
       AND grenzwert_alarm   BETWEEN 0 AND 100);

-- CHECK: nur erlaubte Texte
ALTER TABLE ALGORITHMUS
    ADD CONSTRAINT CK_ALGORITHMUS_RELEASE_STATUS
    CHECK (release_status IN ('alpha', 'beta', 'stable')); -- (3)!

ALTER TABLE EXTREMWERT
    ADD CONSTRAINT CK_EXTREMWERT_TYP
    CHECK (typ IN ('Maximum', 'Minimum'));

-- DEFAULT: ein neuer Extremwert ist zunächst unverarbeitet
ALTER TABLE EXTREMWERT
    ADD CONSTRAINT DF_EXTREMWERT_VERARBEITET
    DEFAULT 0 FOR verarbeitet; -- (4)!
    1. Regel 1 und 2 sind UNIQUE-Constraints. Regel 1 gilt über zwei Spalten gemeinsam — einzeln dürfen sich Verfahren und Version (ver) durchaus wiederholen, nur die Kombination muss eindeutig sein.
    2. Regel 3 und 4 sind CHECK-Constraints mit einem Wertebereich (BETWEEN, beide Grenzen eingeschlossen).
    3. Regel 5 und 6 sind CHECK-Constraints mit einer Liste erlaubter Werte (IN).
    4. Regel 7 ist ein DEFAULT: Wird beim INSERT kein Wert für verarbeitet angegeben, setzt SQL Server 0.

    Tabelle und Constraints in einem Schritt

    Dass hier erst die Tabellen angelegt und die Constraints danach einzeln nachgerüstet wurden, hat didaktische Gründe: So seht ihr jeden Constraint für sich. In der Praxis schreibt man Tabelle und Constraints meist in einer CREATE TABLE-Anweisung — das fertige Gesamtskript am Ende dieses Abschnitts zeigt genau das.

    ALTER TABLE bleibt trotzdem wichtig, denn es gibt Fälle, in denen Constraints nachträglich ergänzt werden müssen:

    • Anforderungen ändern sich in einer bereits laufenden Datenbank (Tabellen und Daten existieren schon, siehe auch der Nachtrag aus Aufgabe 03). Beim Nachrüsten prüft SQL Server allerdings die vorhandenen Daten: Verstoßen sie gegen die neue Regel, wird der Constraint abgelehnt.
    • Zwei Tabellen verweisen gegenseitig aufeinander. Dann kann keine von beiden zuerst mit ihrem Fremdschlüssel angelegt werden; der zweite Fremdschlüssel muss nachträglich ergänzt werden.
    • Große Datenmengen werden importiert. Hier werden Constraints manchmal vorübergehend entfernt oder deaktiviert und danach wieder eingerichtet.

    Vorhersage-Test: Wer lehnt was ab?

    Füllt zuerst die Tabellen mit ein paar Ausgangsdaten (wenn ihr die Tabellen frisch angelegt habt, bekommen die ersten beiden Algorithmen die Nummern 1 und 2 und der Analyse-Lauf die Nummer 1):

    INSERT INTO VERFAHREN (verfahren, grenzwert_meldung, grenzwert_alarm) VALUES
    ('DIN', 60, 80),
    ('PFIX', 50, 75);

INSERT INTO ALGORITHMUS (verfahren, ver, release_datum, release_status) VALUES
    ('DIN', '1.00', '2025-03-01', 'stable'),
    ('DIN', '1.01', '2025-09-15', 'beta');

INSERT INTO ANALYSE_LAUF (zeitstempel) VALUES ('2026-10-26 02:00:00');

    Jetzt kommen sechs weitere Anweisungen. Sagt jeweils vorher voraus: Läuft sie durch oder wird sie abgelehnt? Wenn sie abgelehnt wird: Von welchem Constraint? Führt sie danach in dieser Reihenfolge einzeln aus und vergleicht.

    -- 1
INSERT INTO SCHAEDIGUNG VALUES (1, 1, 45);

-- 2
INSERT INTO SCHAEDIGUNG VALUES (1, 2, 120);

-- 3
INSERT INTO ALGORITHMUS (verfahren, ver, release_datum, release_status)
    VALUES ('DIN', '1.01', '2026-01-10', 'alpha');

-- 4
INSERT INTO ALGORITHMUS (verfahren, ver, release_datum, release_status)
    VALUES ('XYZ', '1.00', '2026-01-10', 'stable');

-- 5
INSERT INTO EXTREMWERT (zeitstempel, typ, wert)
    VALUES ('2026-10-25 13:42:00', 'Maximum', 3.2);

-- 6
INSERT INTO SCHAEDIGUNG VALUES (1, 1, 50);
    Lösung
    Nr. Ergebnis Begründung
    1 läuft durch Lauf 1 und Algorithmus 1 existieren, 45 liegt zwischen 0 und 100.
    2 abgelehnt CK_SCHAEDIGUNG_WERT: 120 liegt außerhalb von 0–100.
    3 abgelehnt UQ_ALGORITHMUS_VERFAHREN_VER: Verfahren DIN in Version 1.01 gibt es schon.
    4 abgelehnt Fremdschlüssel von ALGORITHMUS: Das Verfahren XYZ gibt es in VERFAHREN nicht.
    5 läuft durch verarbeitet fehlt, DEFAULT setzt 0. Mit SELECT * FROM EXTREMWERT könnt ihr das nachsehen.
    6 abgelehnt Primärschlüssel von SCHAEDIGUNG: Die Kombination (1, 1) gibt es seit Anweisung 1 schon.

    Schaut euch die Fehlermeldungen genau an (je nach Installationssprache auf Deutsch oder Englisch): Bei Nr. 2 und 3 steht der Name, den ihr vergeben habt, in der Meldung — man sieht sofort, welche Regel gegriffen hat. Bei Nr. 4 und 6 steht dagegen ein von SQL Server erzeugter Name wie FK__ALGORITHM__verfa__... bzw. PK__SCHAEDIG__..., denn Primär- und Fremdschlüssel haben wir oben in der Kurzschreibweise angelegt, bei der SQL Server den Namen vergibt. Mit so einer Meldung lässt sich schlecht arbeiten — wie ihr auch diese Schlüssel selbst benennt, zeigt der nächste Abschnitt.

    Primär- und Fremdschlüssel mit eigenem Namen

    Die Kurzschreibweise PRIMARY KEY hinter dem Attribut bzw. FOREIGN KEY (...) REFERENCES ... als eigene Zeile ist üblich und funktioniert einwandfrei. Sie ist aber nur die Kurzform der ausführlichen Schreibweise mit CONSTRAINT, und bei der Kurzform vergibt SQL Server den Namen selbst. Ihr könnt diese Namen im Object Explorer ansehen (Datenbank → Tables → Tabelle → Keys); sie sind lang und nichtssagend. Mit CONSTRAINT <Name> bestimmt ihr den Namen selbst — so wie ihr im Relationenschema die Beziehungen auch bezeichnet:

    -- Kurzform: SQL Server vergibt die Namen selbst
algorithmus_id  INT IDENTITY(1,1)  NOT NULL PRIMARY KEY,
FOREIGN KEY (verfahren) REFERENCES VERFAHREN(verfahren)

-- Langform: ihr vergebt die Namen selbst
CONSTRAINT PK_ALGORITHMUS PRIMARY KEY (algorithmus_id),
CONSTRAINT FK_ALGORITHMUS_VERFAHREN
    FOREIGN KEY (verfahren) REFERENCES VERFAHREN(verfahren)

    In der Langform stehen die Constraints als eigene Zeilen unter den Attributen (bei NOT NULL und IDENTITY ändert sich nichts). Das vollständige Skript im Gesamtergebnis unten ist durchgehend so geschrieben: Dort tragen alle Constraints einen Namen, und jede Fehlermeldung nennt die verletzte Regel im Klartext.

    Reihenfolge und Fremdschlüssel

    Zum Schluss noch ein Experiment: Löscht die Tabelle VERFAHREN mit DROP TABLE VERFAHREN;. Was erwartet ihr, und in welcher Reihenfolge müsste man die Tabellen löschen, um die ganze Datenbank sauber abzubauen?

    Lösung

    SQL Server verweigert das Löschen: ALGORITHMUS hat einen Fremdschlüssel auf VERFAHREN, die Tabelle wird also noch gebraucht. Beim Abbau gilt deshalb die umgekehrte Reihenfolge wie beim Aufbau: zuerst die Tabellen, die auf andere verweisen (SCHAEDIGUNG, dann ALGORITHMUS), erst danach die Tabellen, auf die verwiesen wird (VERFAHREN, ANALYSE_LAUF).

CREATE TABLE REAKTOR (
    reaktor_id       VARCHAR(10)  NOT NULL PRIMARY KEY,
    saeureresistent  BIT          NOT NULL
);

CREATE TABLE REZEPT (
    rezept_id  VARCHAR(20)  NOT NULL PRIMARY KEY
);

CREATE TABLE REZEPT_PARAMETER (
    rezept_id       VARCHAR(20)   NOT NULL,
    parameter_name  VARCHAR(30)   NOT NULL,
    wert            DECIMAL(8,2)  NOT NULL,
    PRIMARY KEY (rezept_id, parameter_name),
    FOREIGN KEY (rezept_id) REFERENCES REZEPT(rezept_id)
);

CREATE TABLE CHARGE (
    charge_nr   INT          NOT NULL PRIMARY KEY,
    reaktor_id  VARCHAR(10)  NOT NULL,
    rezept_id   VARCHAR(20)  NOT NULL,
    FOREIGN KEY (reaktor_id) REFERENCES REAKTOR(reaktor_id),
    FOREIGN KEY (rezept_id)  REFERENCES REZEPT(rezept_id)
);

CREATE TABLE PROZESSWERT (
    charge_nr    INT           NOT NULL,
    zeitstempel  DATETIME2(0)  NOT NULL,
    viskositaet  DECIMAL(6,1)  NOT NULL,
    temperatur   DECIMAL(5,1)  NOT NULL,
    fuellstand   DECIMAL(5,1)  NOT NULL
        CHECK (fuellstand BETWEEN 0 AND 100),
    PRIMARY KEY (charge_nr, zeitstempel),
    FOREIGN KEY (charge_nr) REFERENCES CHARGE(charge_nr)
);

    Reihenfolge: REAKTOR und REZEPT haben keine Fremdschlüssel und stehen vorn. REZEPT_PARAMETER und CHARGE verweisen auf sie, und PROZESSWERT verweist auf CHARGE — also kommt PROZESSWERT zuletzt.

    Datentypen: Die Längen (VARCHAR(10), VARCHAR(20)) sind bewusst großzügig gegenüber den Beispielwerten gewählt, aber nicht "so groß wie möglich". Viskosität, Temperatur und Füllstand haben im Beispiel höchstens eine Nachkommastelle; DECIMAL(6,1) und DECIMAL(5,1) genügen. Aus "boolean" wird BIT.

    Constraint: Der Füllstand in Prozent bekommt ein CHECK (fuellstand BETWEEN 0 AND 100) — hier direkt in der Tabellendefinition, denn die Tabelle wird ja gerade erst angelegt.

    Teil D — Gegenprobe mit dem drawDB-Export

    Plant für diesen Teil ca. 10 Minuten ein.

    In Aufgabe 03 habt ihr das Schema der Schnüffel GmbH in drawDB gebaut. drawDB kann daraus selbst ein SQL-Skript erzeugen.

    1. Öffnet euer drawDB-Diagramm aus Aufgabe 03 (Datenbank MSSQL) und exportiert es über Datei → SQL exportieren. (Habt ihr es nicht gesichert, nehmt die Musterlösung zu Aufgabe 03.)

B. euer CHECK für den Füllstand), die Reihenfolge der Anweisungen. Haltet drei Unterschiede fest und bewertet jeweils: Ist das Skript von drawDB besser, schlechter oder nur anders?
    3. Kurzrecherche: drawDB verwendet für Zeitstempel den Typ DATETIME, ihr habt DATETIME2 genutzt. Was unterscheidet die beiden Typen in SQL Server, und welchen empfiehlt Microsoft für neue Datenbanken? (Dokumentation: Microsoft Learn.)
    Musterlösung Teil D anzeigen

    Zu 2 — typische Unterschiede (die genaue Ausgabe hängt von der drawDB-Version ab):

    • Ein Werkzeug exportiert nur, was im Diagramm steht: Ein CHECK für den Füllstand oder benannte Constraints sind nur enthalten, wenn ihr sie dort eingetragen habt. Eigene Skripte enthalten dafür genau die Regeln, die ihr bewusst gesetzt habt.
    • Fremdschlüssel können vom Werkzeug als eigene Anweisungen am Ende erzeugt werden statt innerhalb von CREATE TABLE. Das umgeht Reihenfolgeprobleme, ist aber ein anderer Stil als in der Übung.
    • Datentypen und Längen sind die, die im Diagramm stehen — hier lohnt der Vergleich mit euren eigenen Begründungen.

    Gute Bewertung: Ein exportiertes Skript ist ein brauchbarer Startpunkt, aber kein Ersatz für die inhaltliche Prüfung — dieselbe Haltung wie bei KI-Skripten.

    Zu 3: DATETIME deckt nur Datumswerte ab 1753 ab, ist auf etwa drei Millisekunden gerundet und hat eine feste Genauigkeit. DATETIME2 umfasst einen größeren Datumsbereich (ab dem Jahr 1), erlaubt eine wählbare Genauigkeit (DATETIME2(0) bis DATETIME2(7)) und ist laut Microsoft-Dokumentation für neue Arbeit der empfohlene Typ. Für sekundengenaue Prozessdaten wie hier reicht DATETIME2(0).
